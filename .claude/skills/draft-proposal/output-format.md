# output-format — 저장 파일 구조와 인라인 형식

## 디렉터리 구조

한 실행의 결과는 한 디렉터리에 모인다.

```
projects/outputs/<project>/<YYYY-MM-DD-HHmm>-proposal/
├── 02-main.md           # 본문 10p (각 섹션 + 인라인 추가논의)
├── 01-summary.md        # 요약 1p (본문 완성 후 자동 도출, 끝에 추가논의 한 블록)
└── progress.json        # 재개용 상태
```

- 디렉터리 이름은 새 실행 시작 시점의 로컬 시간을 분 단위까지 박는다.
- 동일 분 단위 디렉터리가 이미 존재하면 뒤에 `-2`, `-3` 접미사.
- `projects/outputs/<project>/` 가 없으면 자동 생성 허용. 그러나 `projects/inputs/`, `projects/outputs/<project>/` 부모 디렉터리는 사용자가 명시적으로 만들어야 한다.

## 02-main.md 형식

양식(`projects/forms/02-main.md`)의 헤더 구조를 그대로 따른다. **각 섹션 본문 직후**에 그 섹션 한정의 인라인 추가 논의 블록을 둔다.

### 한 섹션의 표준 모양

```markdown
### 문제인식

현재 OOO 시장에서는 사용자 OOO명 중 OO%가 ~~한 불편을 겪고 있다.
경쟁 서비스 A·B는 ~~까지는 다루지만 ~~를 다루지 못한다. (가안)

<!--
⚠ 이 섹션 추가 논의 필요 사항
- #DD-1 [근거 부족] "OO% 불편" 수치는 RAW에 없음. 사용자 인터뷰에서 추출 가능하면 정확 수치로 교체.
- #DD-2 [팀 논의 필요] 응답자 N=22 정량 출처. 외부 인용 가능한 통계 출처도 1건 확보.
-->
```

### 인라인 추가 논의 블록 규약

- 항상 **HTML 주석** `<!-- ... -->` 으로 감싼다. 최종 제출 시 주석째 삭제하면 끝.
- 항목 ID는 전체 누적 순번 `#DD-N`. 새 항목 추가 시 `progress.json`의 `dd_counter`를 증가시켜 사용.
- 각 항목은 한 줄로:
  ```
  - #DD-N [<태그>] 한 줄 설명.
  ```
- 표준 태그:
  | 태그 | 의미 |
  | --- | --- |
  | `[팀 논의 필요]` | 팀 합의 안 된 항목. 본인 가안은 있어도 팀 합의 전. |
  | `[근거 부족]` | 본문에 수치·인용이 들어갔지만 RAW 출처 불명. |
  | `[멘토 확인]` | 멘토에게 직접 물어볼 항목. |
  | `[데이터 확보]` | 학습/평가용 데이터 확보 경로 미정. |
  | `[디자인 결정]` | UI/UX·시각 자료 결정 미정. |
  | `[외부 검증]` | 외부 사용자·전문가 검증 필요. |
  | `[확인 필요]` | 그 외 사실 확인 필요. |

### 시각 자료 placeholder

본문 안에 다음 형식의 텍스트 placeholder를 둔다. 자세한 형식은 [`image-suggestions.md`](./image-suggestions.md).

```markdown
### 시스템 구성도

[시스템 구성도 — 권장: Excalidraw.
  포함 요소: 클라이언트(웹/모바일), BFF(NestJS), AI 추론(FastAPI), Postgres, S3, 외부 LLM API.
  스타일: 동기 호출 = 검은 화살표, 비동기 큐 = 점선, AI 경로는 보라색 강조.
  최종 파일: assets/system-diagram.png — 1200px 이상.]

<!--
⚠ 이 섹션 추가 논의 필요 사항
- #DD-7 [디자인 결정] 그림 실제 제작자·일정 미정.
-->
```

## 01-summary.md 형식

양식(`projects/forms/01-summary.md`)의 헤더 그대로. 본문은 인라인 추가논의 없이 깨끗하게. **파일 맨 끝** 한 블록만:

```markdown
... (마지막 섹션 "결과물 활용방안 및 기대효과" 본문)

<!--
⚠ 이 요약본의 추가 논의 필요 사항
- #S-1 [팀 논의 필요] 한 줄 카피 후보 2개: "A안 / B안". 발표 PPT 첫 페이지와 동일하게 가야 함.
- #S-2 [확인 필요] ICT 대분류·중분류 코드.
-->
```

요약본 추가논의 ID는 본문과 구분되는 `#S-N`. `progress.json`의 `s_counter`로 누적 관리.

## 개인정보 마스킹

- **인명**: `김OO`, `OOO 멘토`
- **전화번호**: `010-XXXX-XXXX`
- **이메일**: `xxx@xxx.com`
- **회사·소속명**에 개인 식별 정보가 묶여 있으면 같이 마스킹.

마스킹은 **디스크 쓰기 단계에서만** 적용. 사용자 질문·내부 합본 RAW에는 적용하지 않는다.

## 저장 후 사용자 출력

### 각 섹션 확정 후 (한 줄)

```
✅ '<섹션명>' 저장. (#DD 누적: N개) 다음: '<다음 섹션명>'
```

### 본문 17섹션 모두 끝났을 때

```
📝 본문 17섹션 완료. 01-summary 1p로 압축할까요? (네 / 아직 본문 더 다듬기)
```

### 전체 종료 후

```
🎉 초안 완성.

- 본문: projects/outputs/<project>/<ts>-proposal/02-main.md
- 요약: projects/outputs/<project>/<ts>-proposal/01-summary.md
- 추가 논의: 본문 #DD-N 총 X개 / 요약 #S-N 총 Y개

다음 단계 제안:
1. 팀 회의에서 #DD 항목을 #DD-1부터 순차 결정. 결정될 때마다 본문 placeholder를 실제 내용으로 교체.
2. 본문에 들어간 **Mermaid 코드블록을 PNG 이미지로 교체**. GitHub / Notion / Mermaid Live Editor에서 렌더링 후 export → `assets/` 디렉터리에 저장 → 이미지 마크다운으로 교체. (PDF 변환기가 Mermaid를 그대로 텍스트로 박을 수 있음.)
3. 그 외 시각 자료 placeholder(와이어프레임·인터뷰 카드 등)를 실제 이미지로 교체.
4. `/analyze-meeting <project> planning` 으로 4페르소나(tech-lead / target-user / swm-reviewer / peer-competitor) 검토 받기.
5. 본문 인라인 주석(<!-- ... -->)을 최종 제출 시 모두 제거.
```

## 양식 매핑 주의

- 양식의 파란색 안내 문구(`<!-- 사용자가 직면한 문제나 ... -->` 등)는 **본문 작성 시 모두 삭제**한다. 인라인 추가논의 주석과 양식 안내 주석이 섞이지 않도록 주의.
- 양식의 표(`| 기능 | 설명 |` 등)는 그대로 본문에 두고 셀을 채운다. 표 직후에 인라인 추가논의 주석 블록을 둘 수 있다.
- 양식의 `[시스템 구성도 이미지/다이어그램 삽입]` 같은 코드블록 placeholder는 [`image-suggestions.md`](./image-suggestions.md)의 표준 포맷으로 교체.
