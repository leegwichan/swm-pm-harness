# execution — 실행 절차

`draft-proposal` skill이 호출되면 메인 Claude는 아래 단계를 순서대로 수행한다. 입력 파싱과 검증은 [`invocation.md`](./invocation.md), 출력 형식은 [`output-format.md`](./output-format.md), 질문 후보는 [`questions-bank.md`](./questions-bank.md) 참조.

## 1) 입력 로드

1. [`invocation.md`](./invocation.md)의 검증을 통과시킨다.
2. `projects/inputs/<project>/**/*.{md,html,txt,csv}`를 `Glob`으로 모은다. 파일명 오름차순으로 정렬.
3. 각 파일을 `Read`하여 다음 형식으로 하나의 합본 RAW DATA 문자열을 구성한다.
   ```
   === FILE: <상대경로> ===
   (파일 내용)
   === END FILE: <상대경로> ===
   ```
4. 이미지 파일(`.png/.jpg/.jpeg`)은 별도 `INPUT_IMAGES` 메타 리스트로 적어둔다 (경로 + 파일명만). 시스템 구성도·와이어프레임 등 본문 삽입 가능 여부를 해당 섹션에서 사용자에게 묻는다.
5. RAW 합본이 단일 호출로 처리하기 부담스럽게 크면 자동 절단하지 말고 사용자에게 "특정 기간/파일 범위로 좁힐지" 묻는다.

## 2) 양식 골격 로드

- `projects/forms/02-main.md` 와 `projects/forms/01-summary.md`를 `Read`해서 양식 구조를 인지한다.
- 신규 모드라면 출력 디렉터리에 양식 골격(파란색 안내 문구는 그대로 남겨두고)을 복사해 빈 파일을 만든 뒤 섹션을 채워간다.
- 재개 모드라면 기존 `02-main.md`를 `Read`해서 마지막 확정 섹션을 식별.

## 3) 본문(02-main.md) 11개 섹션을 인터리브로 진행

본문 양식 기준 11개 섹션. **`--sections <spec>` 이 지정되었으면 그 부분집합만** 인터리브 진행. 각 섹션마다 아래 4단계 사이클을 돈다.

| # | 섹션 | 양식 헤더 |
| --- | --- | --- |
| 1 | 문제인식 | `## 목적 및 필요성 → ### 문제인식` |
| 2 | 기획의도 | `### 기획의도` |
| 3 | 프로젝트 소개 | `## 프로젝트 개요 → ### 프로젝트 소개` |
| 4 | 주요 기능 | `### 주요 기능` (표) |
| 5 | 시장분석 | `### 시장분석` |
| 6 | 시스템 구성도 | `### 시스템 구성도` (이미지/다이어그램) |
| 7 | 개발환경 | `### 개발환경` (표) |
| 8 | AI 활용 전략 | `### AI 활용 전략` |
| 9 | 팀 구성 및 역할 + 멘토 구성 및 역할 + 추진 일정 + 수행 방법 + 예상문제 | `## 프로젝트 수행 방안` 묶음 |
| 10 | 결과물 형태 + 활용방안 + 기대효과 | `## 결과물 및 기대효과` 묶음 |
| 11 | 담당멘토 의견 | `## 담당멘토 의견` (표) |

> 분담 모드 예: `--sections 6-9` 라면 위 표의 6·7·8·9번 행만 사이클을 돈다. 9번은 묶음 섹션이므로 그 안의 하위 항목(팀 구성 / 멘토 / 일정 / 수행 방법 / 예상문제)을 한 묶음으로 다룬다. 지정되지 않은 섹션은 양식 골격 그대로 둔다 — 다른 팀원이 별도 호출(`--resume <ts> --sections <other-spec>`)로 채운다.

### 섹션 사이클 (각 섹션마다 반복)

#### (a) 초안 제시
- RAW DATA에서 그 섹션과 관련 있는 발언·자료를 인용하면서 초안을 작성한다. 인용 발언은 발화 출처(파일명·날짜)를 본문 옆 주석으로 남기되, **본문 텍스트 자체는 제출용 톤으로** 작성한다.
- RAW에 정보가 명백히 부족한 부분은 본문에 `[? RAW 없음 — 사용자 확인 필요]` 마커로 표시.
- 인터뷰 영상/사용자 검증/데이터 출처/벤치마크 수치 등 외부 후기에서 자주 지적되는 항목은 [`questions-bank.md`](./questions-bank.md)의 섹션별 항목으로 자동 자가검증.

#### (b) 핵심 질문 1~3개
- [`questions-bank.md`](./questions-bank.md)에서 해당 섹션 후보 질문 중, RAW로 풀리지 않은 것 1~3개만 추려서 사용자에게 던진다.
- 4개 이상은 한 번에 묻지 않는다 (피로감). 꼬리 질문은 사용자 답변 후 별도 라운드로.

#### (c) 사용자 답변 반영
- 답변이 명확하면 본문 초안에 직접 반영.
- 답변이 "팀에서 논의 안 됨 / 판단 불가 / 데이터 없음 / 모름" 류면 그 섹션 본문 직후에 `<!-- ⚠️ 추가 논의 필요 -->` 인라인 블록을 만들고 placeholder(`[팀 논의 후 작성 — 항목: OOO]`)로 본문을 채운 뒤 다음 섹션으로 진행. 멈추지 않는다.
- 답변에서 새로운 키워드/사실이 나오면 이후 섹션에도 일관성 있게 반영한다.

#### (d) 부분 저장
- 그 시점까지의 `02-main.md`를 `Write`로 덮어쓴다.
- 저장 시 [`output-format.md`](./output-format.md)의 마커 규칙을 따른다 (확정 섹션 마커, 추가 논의 블록 형식).
- 마스킹은 이 시점에 적용.

### 시각 자료가 필요한 섹션 (Mermaid 자동 생성)

디폴트로 본문에 **Mermaid 초안 + placeholder 제작 가이드**를 함께 삽입한다. Mermaid 노드·관계는 RAW DATA에서 추출한 컴포넌트·일정·플로우를 기반으로 [`image-suggestions.md`](./image-suggestions.md)의 "섹션별 Mermaid 권장 패턴"에 채워 넣는다.

사용자 답변에 따라 본문 정리:

- "Mermaid로 충분" / "이걸로 가자" → placeholder 가이드 블록을 인라인 추가논의로 이동. 본문에는 Mermaid만 남김.
- "직접 그릴게" / "Excalidraw·Figma로 따로" → Mermaid 블록 삭제. placeholder만 유지. 인라인 추가논의에 `[디자인 결정] 그림 제작 담당·일정 미정` 누적.
- "Mermaid 일부 수정" → 코드 수정 반영. placeholder도 같이 유지.
- 답 없음 → 둘 다 본문에 그대로 두고 다음 섹션 진행.

대상 섹션별 출력 형태:

- **6번 시스템 구성도** — `flowchart LR` 자동 생성. RAW에서 등장한 클라이언트·서버·DB·외부 API·AI 추론 모듈을 노드로. 노드 5~8개 제한.
- **5번 시장분석** — 경쟁 서비스 비교는 표로 충분. 시장 규모 그래프가 필요하면 Mermaid는 부적합 — placeholder만.
- **8번 AI 활용 전략** — `flowchart TD`로 데이터 플로우 자동 생성. 입력 → 전처리 → 모델 추론 → 후처리 → 응답 + 평가 지표 노드(점선).
- **9번 추진 일정** (묶음 안) — 양식 표가 기본. PPT용으로 추가하고 싶다면 `gantt` 자동 생성. 사용자가 명시적으로 원할 때만 본문에 둠.
- **10번 결과물 형태** (묶음 안) — 와이어프레임은 Mermaid로 표현 어려움. placeholder만 + 인라인 추가논의에 `[디자인 결정]`.

최종 PDF 제출 전에 **Mermaid 코드블록은 렌더링한 PNG 이미지로 교체**해야 함을 [`output-format.md`](./output-format.md)의 마무리 메시지에서 안내한다.

## 4) 요약본(01-summary.md) 자동 도출

본문 11개 섹션이 모두 확정된 뒤에 진행한다.

> **`--sections` 로 부분 진행 중인 경우 이 단계는 건너뛴다.** 분담된 섹션만 채우고 5)로 직행. 모든 섹션이 채워진 뒤 누군가 `--sections` 없이 `--resume <ts>` 로 호출하면 그때 요약본이 도출된다.

1. 본문에서 다음을 추출해 1p 요약을 작성:
   - 프로젝트명 (서비스명 + 한 줄 카피)
   - 프로젝트 소개 3줄 (본문 3번 섹션 압축)
   - 기술 키워드 3~5개 (본문 7·8번 섹션에서 추출)
   - ICT 연구개발 기술 분류 (사용자 확인 필요 — 양식에 대분류·중분류 빈 칸)
   - 팀 정보 (사용자 확인 — 팀명 정해졌는지)
   - 목적 및 필요성 (본문 1·2번 압축)
   - 프로젝트 개요 (본문 3·4·5번 압축)
   - 프로젝트 수행방안 (본문 9번 묶음 압축)
   - 결과물 활용방안 및 기대효과 (본문 10번 묶음 압축)
2. 양식 분량(1p) 안에 들어가도록 각 항목을 압축. 본문에서 그대로 베끼지 말고 헤드라인 톤으로 다시 쓴다.
3. 본문에 있던 추가 논의 사항 중 1p 요약에도 영향을 주는 항목(예: 프로젝트명 미확정, 팀명 미확정, ICT 분류 미확정)은 요약본 맨 끝에 한 블록으로 모은다 — [`output-format.md`](./output-format.md)의 `01-summary` 블록 규칙 참조.
4. 요약본 파일을 `Write`로 저장.

## 5) 마무리 출력

저장 후 사용자에게 다음 정보만 짧게 전달.

### 전체 모드 (`--sections` 미지정)

```
✅ draft-proposal 완료

저장 위치: projects/outputs/<project>/{ts}-proposal/
파일:
  - 02-main.md (10p 본문)
  - 01-summary.md (1p 요약)

추가 논의 필요 사항: N개 (02-main.md 인라인 + 01-summary.md 말미)

다음 액션 제안:
  1. 02-main.md의 ⚠️ 블록을 팀 회의에서 결정 → 동일 위치 채우기
  2. 시스템 구성도 이미지 첨부 (placeholder 자리)
  3. 멘토 한줄평 3명 수령 후 11번 섹션 채우기
  4. 모든 ⚠️ 블록 비워졌으면 PDF 변환 후 제출본 검증
```

### 분담 모드 (`--sections` 지정)

```
✅ draft-proposal 부분 진행 완료 (섹션: {spec})

저장 위치: projects/outputs/<project>/{ts}-proposal/
파일:
  - 02-main.md (담당 섹션만 채워짐, 나머지는 양식 골격 그대로)
  - 01-summary.md (이번 호출에서는 도출하지 않음)

추가 논의 필요 사항: N개 (담당 섹션 인라인)

다음 액션 제안:
  1. 담당 섹션의 ⚠️ 블록을 팀 회의에서 결정 → 동일 위치 채우기
  2. 다른 팀원이 자기 담당 섹션을 같은 디렉터리에 채우기:
     /draft-proposal <project> --resume {ts} --sections <다른 spec>
  3. 모든 섹션이 채워지면 누군가 --sections 없이 한 번 더 호출해 요약본 도출:
     /draft-proposal <project> --resume {ts}
```

전체 본문을 다시 채팅에 토해내지 않는다. 사용자가 파일을 직접 연다는 가정.

## 6) 마스킹

이름/연락처/이메일 마스킹 규칙은 [`output-format.md`](./output-format.md) 참조. 사용자 채팅 화면에는 마스킹하지 않는다 — 디스크 저장 시에만.
