## 0. 응답 측정 기준 설정 방법론 (Industry Practice)

기업이 NFR/QAS의 "응답 측정" 수치를 설정할 때 사용하는 6가지 일반적인 접근법이다. **각 QAS는 이 중 하나 이상을 근거로 수치를 도출**해야 하며, 본 문서의 모든 수치는 §3에서 어떤 근거를 사용했는지 명시한다.

### 0.1 SLI/SLO 기반 (Service Level Indicator / Objective)

- **방법**: Google SRE의 *4 Golden Signals*(latency / traffic / errors / saturation)로 SLI를 정의하고, 비즈니스가 허용하는 손실 수준에서 SLO를 합의한다. 남는 여유분 = **Error Budget**.
- **수치 표현**: 분포 기반(P50 / P95 / P99). 평균값은 long tail을 가려 부적합.
- **출처**: Google SRE Workbook(공개 문서).
- **언제 쓰나**: 응답 시간·가용성·에러율처럼 분포가 의미 있는 지표.

### 0.2 사용자 인지 한계 기반 (Human Perception)

- **방법**: 인간의 인지·집중 한계 값을 응답 시간 목표로 환산.
- **대표 수치**:
  - **0.1초**: 즉각 반응으로 인지(Nielsen 1993).
  - **1초**: 사용자 사고 흐름 유지 한계(Nielsen 1993).
  - **400ms (Doherty Threshold)**: IBM 1982 — 생산성 급변점.
  - **10초**: 사용자 주의 한계(Nielsen 1993).
- **출처**: Nielsen Norman Group "Response Times: The 3 Important Limits" (1993), Doherty & Thadhani 1982.
- **언제 쓰나**: UI 인터랙션·실시간 표시 같은 사용자 직접 인지 영역.

### 0.3 비즈니스 KPI 역산 (Business-Driven)

- **방법**: 매출·이탈률·전환율 등 KPI를 응답 목표로 역산.
- **대표 인용**: Akamai/Amazon 사례(100ms 지연 → 약 1% 매출 감소) 등.
- **언제 쓰나**: 결제 / 검색 / 상품 페이지처럼 KPI 연결이 직접적인 경로.
- **본 프로젝트 적용**: WTP(동아리 5,000~10,000원)에서 역산한 LLM 비용 상한.

### 0.4 벤치마크 / 경쟁사 비교 (Competitive Benchmarking)

- **방법**: 동일 도메인 경쟁 서비스의 공개 수치 또는 자체 측정값을 베이스라인으로 사용.
- **언제 쓰나**: 시장에 유사 서비스가 있어 사용자가 이미 학습된 기대치를 갖는 경우.
- **본 프로젝트 적용**: 클로바노트·Otter.ai 응답 속도, 한국어 STT 벤더 WER 비교.

### 0.5 기술적 한계 기반 (Technical Floor)

- **방법**: 외부 API latency / 네트워크 RTT / 하드웨어 처리 시간 등 **시스템이 물리적으로 도달 가능한 하한 + 안전 마진**.
- **공식 예**: `목표 latency = 외부 API P95 + 네트워크 RTT + 자체 처리 + 20~30% buffer`.
- **언제 쓰나**: 외부 의존성이 핵심 경로에 있는 경우. 본 프로젝트의 STT/LLM 호출이 정확히 이 경우.

### 0.6 표준·규제 기반 (Compliance)

- **방법**: 외부 표준(NIST, OWASP, ISO, WCAG)이나 법(GDPR, 개인정보보호법)이 명시한 수치를 그대로 사용.
- **대표 예**:
  - **NIST SP 800-63B** — 인증 토큰 엔트로피 ≥ 112 bits.
  - **GDPR Art. 17** — 삭제 요청 처리 "without undue delay"(통상 30일 권장).
  - **SSL Labs** — TLS 등급 A 이상.
- **언제 쓰나**: 보안·개인정보 영역.

### 0.7 점진적 목표 (Stretch Goal / Maturity Ladder)

- **방법**: Baseline(현 측정값) → 1차 목표 → 최종 목표의 사다리식 목표 설정. 무리한 단일 목표 대신 분기·릴리즈별 단계 상향.
- **언제 쓰나**: 모델·알고리즘 정확도처럼 단번에 도달 어려운 지표.
- **본 프로젝트 적용**: WER 50% → 25% → 15% 단계 상향(이OO 멘토 권고).

## 1. F1 기능 요약 (NFR 정의의 전제)

### F1-1) STT 토론 속기록
- 토론 음성 청크(1~3초) → BFF → STT API → 발화 텍스트 산출
- **화자 분리·찬/반 분리·내용 정제** 포함
- STT 결과는 즉시 좌측 패널 표시, 누적 발화는 **주기적 LLM 보정**으로 정제본 덮어쓰기 (구체 SLO는 §3.1 QAS-PE-01·02 참조)

### F1-2) 쟁점 요약
- 정제 발화 → LLM 쟁점-주장-근거 3단 트리 **주기적 추출** (구체 SLO는 §3.1 QAS-PE-03 참조)
- 메인 대시보드 split view 우측에 갱신, **쟁점별 찬반 근거 매핑** 포함

### 공통 제약
- 한국어 4인 세다 토론, 토론 1회 = 40~50분, ~6,000자
- 다중 viewer 동시 구독, 중간 합류·재접속 복구 필수
- Redis Pub/Sub 백플레인 + SQS 비동기 워커
- STT 1차 후보: **AWS Transcribe Streaming · Azure Speech Realtime**
- LLM 1차 후보: 보정(GPT-4o-mini / Claude Haiku / Gemini Flash 등), 쟁점 추출(GPT-4o / Claude Sonnet / Gemini Pro 등)

## 3. QAS — 품질 속성 시나리오 (기준 설정 근거 + 도달 확인 방법 포함)

> 각 시나리오는 (a) 6요소 표 → (b) **기준 설정 방법·근거**(§0의 어느 방법론 사용했는지) → (c) **도달 확인 방법**(어떻게 측정·검증하는지) 순으로 작성한다.

### 3.1 성능 효율성 (Performance Efficiency)

#### QAS-PE-01 — STT 변환 응답 지연 (F1-1)

| 요소 | 내용 |
|------|------|
| 자극원 | 토론 참여자(발화자) |
| 자극 | 음성 청크 전송(1~3초) |
| 환경 | 정상 운영, 동시 세션 N ≤ `(TBD)`, 토론 시간 0~50분 |
| 대상 | BFF + STT API + WebSocket broadcast 경로 |
| 응답 | 발화 텍스트(원문)를 대시보드 좌측에 표시 |
| 응답 측정 | **음성 청크 종료 → 텍스트 표시까지 P95 ≤ 4초, P99 ≤ 6초** |

**기준 설정 방법 (근거)**

- **§0.1 SLO 기반**: P95/P99 백분위 사용. 평균은 long tail을 가리므로 부적합.
- **§0.5 기술적 한계 (도출)**: AWS Transcribe Streaming은 partial result를 약 200~500ms, final result(stabilized) 약 0.5~1.5초에 산출하는 것이 일반적이다 — *벤더 공식 한국어 SLA 미공개, 자체 PoC 측정 필요*. 여기에 BFF 처리(약 50~150ms) + WebSocket broadcast(약 100~300ms) + 모바일 네트워크 변동(약 200~500ms)을 합산하면 종단 latency 1.0~3.0초 typical. 30% 안전 마진 → **P95 ≤ 4초**, P99는 추가 1.5× buffer → **6초**.
- **§0.2 사용자 인지**: 실시간 자막(live captioning) 산업 베이스라인 5~8초(*FCC live captioning 표준 6초 — 정확 인용 확인 필요*) → 4초는 그 안에서 사용자 우위 체감. Nielsen "10초 = 주의 한계"의 절반 수준.
- **§0.4 벤치마크**: Otter.ai·클로바노트 등 범용 회의 STT의 실시간 표시 지연(*공식 SLA 미명시, 자체 측정 필요*)을 베이스라인으로 동등 이하 목표 — "토론 전용 도구가 범용 회의록보다 느릴 이유가 없다"는 차별화 한 줄의 정량 근거.

**도달 확인 방법**

1. **PoC 단계**: 합성 음성 청크 1,000개 → BFF 경유 STT 호출 → 종단 latency를 jiwer/자체 스크립트로 수집 → histogram → P95·P99 산출.
2. **CI 단계**: k6 시나리오로 30 RPS × 10분 부하 테스트, P95 결과를 임계 게이트로 등록.
3. **프로덕션**: Pinpoint 분산 트레이싱 + Prometheus histogram(`http_request_duration_seconds`), Grafana 패널에서 7일 rolling P95 추적. SLO 위반 시 Error Budget 차감.

#### QAS-PE-02 — LLM 텍스트 보정 갱신 주기 (F1-1)

| 요소 | 내용 |
|------|------|
| 자극원 | 누적 발화 버퍼 |
| 자극 | 보정 주기 도달 (10~20초) |
| 환경 | 정상 운영, AI Worker 정상 |
| 대상 | LLM 보정 워커 + Redis Pub/Sub |
| 응답 | 정제본으로 발화 카드 덮어쓰고 broadcast |
| 응답 측정 | **갱신 주기 15~30초, 워커 트리거 → 표시 P95 ≤ 35초** |

**기준 설정 방법 (근거)**

- **§0.2 사용자 인지 (상한 30초)**: 보정은 *덮어쓰기*이므로 STT 원문이 이미 표시된 상태 — 사용자가 능동적으로 보정 완료를 기다리지 않는다. Nielsen "10초 = 주의 한계"의 약 3배까지 *background update* 완화 적용 → cycle 상한 30초.
- **§0.5 기술적 한계 (하한 15초)**: 저비용 LLM(GPT-4o-mini / Claude Haiku 등) 단일 호출 평균 latency 1~5초 + SQS 큐잉 0~2초 + broadcast 0.3초 = 단일 호출 종단 3~8초(*벤더 공식 한국어 latency 확인 필요*). cycle을 단일 호출 평균(약 4초)의 약 4배 이내로 두어 큐잉 정체·재시도 흡수 → cycle 하한 15초.
- **§0.3 비즈니스 KPI 역산 (하한 보강)**: 호출 빈도 = 직접 비용. 1세션 50분 기준 cycle 5초 = 약 600회/세션, cycle 15초 = 약 200회/세션, cycle 30초 = 약 100회/세션. 동아리 WTP(5,000~10,000원/월)와 토큰 단가(*2026-05 기준 확인 필요*) 역산 시 15~30초 cycle이 손익 sweet spot.
- **§0.5 기술적 한계 (P95 35초)**: 단일 호출 P95 약 8초 + 큐 정체 시 추가 대기 약 15초 + 재시도 1회 buffer = **35초**.
- **§0.7 점진적 목표**: PoC에서 베이스라인 측정 후 cycle을 15초 → 20초 → 30초 사이에서 비용·정확도 최적점으로 조정.

**도달 확인 방법**

1. **워커 메트릭**: SQS `ApproximateAgeOfOldestMessage`, Worker 처리 시간을 CloudWatch 또는 Prometheus로 수집.
2. **종단 측정**: 발화 INSERT 시각 ↔ broadcast 시각 차이를 BFF 로그에 기록 → 일/주 단위 P95 산출.
3. **부하 테스트**: 동시 5세션 × 50분 시나리오로 큐 적체 발생 여부 확인.

#### QAS-PE-03 — 쟁점 트리 갱신 주기 (F1-2)

| 요소 | 내용 |
|------|------|
| 자극원 | 누적 정제 발화 |
| 자극 | 쟁점 추출 주기 도달 또는 발화 임계치 도달 |
| 환경 | 정상 운영, 토론 진행 중 |
| 대상 | LLM 쟁점 추출 워커 + Postgres + Redis Pub/Sub |
| 응답 | 쟁점-주장-근거 트리 + 쟁점별 찬반 근거 매핑 broadcast |
| 응답 측정 | **갱신 주기 20~40초, 트리거 → broadcast P95 ≤ 50초** |

**기준 설정 방법 (근거)**

- **§0.2 사용자 인지 (상한 40초)**: 쟁점 트리는 *덮어쓰기보다 추가*에 가까워 사용자 능동 모니터링 부담이 더 낮다. 다만 "라이브한가" 의심 한계까지는 가지 말 것 — Nielsen 10초 한계의 약 4배 = **상한 40초**.
- **§0.5 기술적 한계 (하한 20초)**: 고품질 모델(GPT-4o / Claude Sonnet / Gemini Pro 등) 단일 호출 latency 2~8초이며 *누적 발화 토큰 길이에 비례 증가* — 토론 후반 누적 텍스트 약 6,000자 시점에서 P50 약 10초까지 증가 추정(*자체 PoC 측정 필요*). SQS 큐잉 0~3초 합치면 단일 호출 5~15초. cycle을 평균 호출 시간(약 10초)의 2배 이상으로 두어 토큰 증가 흡수 → **하한 20초**.
- **§0.3 비즈니스 KPI 역산**: 고품질 모델은 저비용 모델 대비 토큰 단가 약 10~30배(*벤더별 2026-05 시점 확인 필요*). 호출 빈도를 보정(PE-02)보다 약 1.3~1.5배 길게 두는 것이 비용 합리 → cycle 20~40초가 PE-02(15~30초)의 적정 배율.
- **§0.5 기술적 한계 (P95 50초)**: 토론 후반 단일 호출 P95 약 20초까지 늘어날 수 있음 + 큐 정체 buffer 약 20초 + 재시도 1회 = **50초**.
- **§0.7 점진적 목표**: 1차 cycle 30초로 시작, 누적 토큰 길이별 latency 회귀선 측정 후 최적점 조정.

**도달 확인 방법**

1. **워커 메트릭**: PE-02와 동일 (`SQS age`, 처리 시간).
2. **LLM API 메트릭**: OpenAI/Anthropic usage API에서 호출당 latency·token 수 수집.
3. **부하 테스트**: 발화 누적 길이를 변수로 한 시나리오(0/10/30/50분 시점) → latency 회귀선 도출 → 25초 위반 시점 식별.

2. **단위 테스트**: BFF의 발화 ID 단조 증가 보장 + 클라이언트 last-received-id 기반 재요청 로직 테스트.
3. **프로덕션 메트릭**: 재연결 이벤트 발생 시 손실 발화 수를 Sentry에 metric으로 송신.

## 4. 우선순위 — **취업 임팩트 단일축**
