## 기술적 난이도 타당성

- 현재 난이도 수준: **적정 ~ 과욕 경계** (특히 백엔드 쪽이 과욕, 프론트 쪽은 적정)
- 근거:
  - 백엔드: 실시간 4화자 한국어 STT + 화자 분리 + LLM 논증 구조 추출(주장-근거-반박-재반박 트리) + 실시간 쟁점별 우세 판정. 각각의 서브 문제가 단독으로도 SWM 한 학기 분량. 5/14 이OO 멘토가 "Sprint 1-1: 화자 구분(같은 사람 먼저)"으로 후퇴 권고한 것은 이미 백엔드가 과욕임을 멘토도 인지한 신호.
  - 화자 다이어리제이션(diarization)은 한국어 4인 동시 발화 환경에서 상용 API도 WER/DER 보장 못함 — **확인 필요**. STT API 선정 벤치마크(O-204) 미완.
  - 프론트: 실시간 데이터 상태 관리 + 원문-분석 양방향 링크 + resizable split + 마인드맵 부분 리렌더링은 적정 난이도. 5/6 멘토가 "useTransition, 티어링, 마이크로 스토어 비교"로 면접 서사 명확화한 부분은 적정.
  - LLM 부분: Bedrock + Spring AI 선택은 면접관 호환성 측면에서 합리적. 다만 "LLM Judge가 쟁점별 우세 판정"은 정답셋 없이 검증 불가. 황OO 멘토가 "실제 토론 10+개 데이터셋 + 사람 정답 요약 + LLM-as-judge 평가"를 권고했으나 5/14까지 정답셋 구축 일정 미명시.
- 조정 필요 부분:
  - **백엔드 핵심 기여를 1개로 압축**: "실시간 스트리밍 STT + 분산 환경 세션 복구(끊김/재연결 시 녹음·상태 이어쓰기)" 또는 "논증 구조 추출 파이프라인(LLM Judge 정답셋 기반 평가 포함)" 중 택 1. 둘 다 하면 둘 다 어설프게 끝남.
  - 논증 구조 추출이 LLM 단일 프롬프트 콜이면 "래퍼"로 평가됨. 다단계(쟁점 클러스터링 → 발언 매핑 → 우세 판정) + 평가 루프 + 자체 데이터셋이 있어야 기여로 인정.
